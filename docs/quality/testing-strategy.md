# Testing Strategy

## Status

**Current and Planned.** Reconciled with Prototype 1 in Phase B0 (2026-10-18).

## Goals

- Protect existing behavior during refactoring
- Verify business rules independently of frameworks
- Avoid live external calls during normal tests
- Test errors and edge cases, not only successful paths
- Make results repeatable and deterministic
- Never claim an algorithm improvement without comparison evidence

## How to Run

### Backend

From `backend/`, with the backend virtual environment active:

```text
python -m pytest -q
```

The suite must run from `backend/`, because tests import `src.…` and there is no pytest configuration file. `tests/conftest.py` (B1) provides database fixtures only. At B0, running from the repository root failed collection with 8 import errors. Outside the venv, the system Python on the B0 machine has no pytest.

Persistence tests create their own SQLite files under pytest's `tmp_path` and upgrade them with the real migrations. They never open `backend/data/intentune.db` or depend on `DATABASE_URL`.

Run the full suite after every phase (spec §28).

### Frontend

From `frontend/`:

```text
npm test                # Vitest: unit, static-render and DOM tests
npm run build           # typecheck and production build
npm run lint            # oxlint
npm run check:browser   # headless-Chrome browser checks (not part of npm test)
```

## Current Test Coverage

### Backend

The original project tests areas including:

- CSV loading
- Type conversion
- Perfect and partial matches
- Numerical validation
- Ranking
- Top-k behavior
- Empty input
- Negative `k`
- Deterministic tie-breaking
- Mutation protection
- CLI integration

The existing suite is the regression baseline.

Added during the canonical domain refactor:

- `tests/test_canonical_scoring.py` and `tests/test_canonical_ranking.py` exercise typed domain objects without CSV or legacy dictionary inputs.
- `tests/test_csv_catalog.py` verifies CSV-row dictionaries, numeric conversion, optional metadata, catalog loading, `CsvCatalog`'s conformance to the `Catalog` port, and the adapter's lack of printing side effects.
- `tests/test_catalog_port.py` verifies the `Catalog` protocol's structural typing: an object with `list_candidates()` satisfies it, one without does not.
- `tests/test_recommendation_service.py` verifies application-level orchestration and type boundaries, including `recommend_from_catalog()` against an in-memory fake catalog (ranking determinism, result limits, empty catalog, non-`Catalog` rejection).
- `tests/test_legacy_compatibility.py` covers legacy-to-canonical conversion, the documented top-five baseline, and behavioral equivalence between legacy and canonical results across all 20 songs.

Added in B1 (persistence foundation):

- `tests/test_listener_profile.py`: `ListenerProfile` validation (canonical UUID, bool flag, timezone-aware UTC time, immutability) and default-listener generation.
- `tests/test_local_listener_service.py`: pure application tests of `ensure_default_listener()` against an in-memory fake unit of work, with no SQLite.
- `tests/test_persistence_db.py`: `DATABASE_URL` resolution (default, relative to `backend/` regardless of working directory, `.env.example` agreement, absolute and in-memory URLs, non-SQLite rejection); connection setup (foreign keys enforced and actually rejecting an orphan row, WAL, transactional DDL proven by a rolled-back `CREATE TABLE`); `UtcDateTime` round trips, offset conversion, and naive rejection.
- `tests/test_migrations.py`:
  - **Upgrades:** a clean upgrade from an empty database; a single head; a path with spaces and `%`.
  - **Schema:** the `listener_profiles` columns, non-null constraints, primary key, and the unique index on the default flag, checked through stable reflected fields (names, columns, the unique flag) rather than whole reflected dictionaries or raw DDL text.
  - **Snapshots:** a no-op re-upgrade and an upgrade–downgrade–upgrade round trip, each compared against a before/after schema snapshot; downgrade to base removing every table the ORM declares.
  - **Code agreement:** migrations matching the ORM records (`compare_metadata`).
  - **One default listener, by behavior:** a second default is refused on both INSERT and UPDATE, and several non-default rows are allowed.
  - **Atomic failure:** a deliberately failing migration changes the schema, confirms the change, then raises. The schema and existing data are left unchanged. A failing upgrade from an empty database leaves no partial schema, not even `alembic_version`. Both tests fail when B1's transaction handling is removed.
- `tests/test_listener_repository.py`: repository reads and writes against a migrated database; unit-of-work commit, rollback on exit, exception, or explicit rollback, isolation between transactions, reuse, non-re-entrancy, and refusal outside `with`; the default listener end to end, including idempotence and survival across an engine restart.
- `tests/test_architecture_boundaries.py`: covers every Python file under `domain/`, `ports/`, and `application/`, including nested subpackages. None may import a storage or delivery framework (mutagen too, since B2; soundfile and numpy, since B3), a filesystem module (`os`, `shutil`, `pathlib`, `glob`, `io`, `tempfile`, `stat`; since B2), or the persistence or adapter packages. The domain may import nothing from `src` outside itself. Relative imports are resolved to absolute module names before checking. Self-tests cover the resolver and plant violations in a synthetic nested package to prove they are caught.

Added in B3 (background analysis):

- `tests/test_analysis_domain.py`:
  - **Jobs:** every transition and invariant (skip reasons versus failure reasons, RUNNING needs a claim); retry and interruption until attempts run out; which jobs may be re-armed.
  - **Rules:** the needs-analysis rule; analyzer identity.
  - **Features:** values must be finite and non-negative; unknown names such as `tempo_bpm` are refused; measurements carry provenance and no confidence.
- `tests/test_signal_levels.py`: real WAV, FLAC, Ogg Vorbis, Opus, and MP3 tones encoded by libsndfile.
  - **Exact values:** lossless formats measure the expected peak, RMS, and duration. For lossy formats, block-by-block results equal a whole-file computation on the same decoded samples.
  - **Signal cases:** silence measures zero; levels scale with amplitude; a peak after the first read block is found; mono and stereo match.
  - **Bad input:** undecodable content raises a decode error that names no path; a missing file raises `OSError`; M4A is not supported.
- `tests/test_analysis_repositories.py`:
  - **Jobs:** round trips; one job per track and analyzer version.
  - **Claims:** `claim_next` takes the oldest pending job, counts an attempt, clears the last failure, never takes non-pending jobs, and never hands one job to two units of work.
  - **Features:** replacement per analyzer.
  - **Constraints:** CHECK constraints for job statuses, reasons, and kinds, and feature names (`energy`, `danceability`, and `tempo_bpm` are refused).
- `tests/test_analysis_service.py`:
  - **The guide's four B3 tests:** tracks usable, and the library writable, during analysis; a failing track not stopping the others; interrupted jobs recovering; reanalysis after a version change.
  - **Queuing:** idempotent; skips missing and analyzed tracks.
  - **Outcomes:** decode errors not retried; read errors retried then failed; unsupported formats skipped; a missing managed copy re-queued after repair; superseded jobs re-armed by their own version (a regression test for a bug found in manual verification).
  - **Messages:** no file paths.
  - **End to end:** the real `SignalLevelAnalyzer`.
- `tests/test_analysis_worker.py`: a real thread against a real database, waiting on observable state with deadlines. It covers draining the queue, waking for new tracks, surviving a failing job, surviving errors outside a job, recovering on start, `stop()` letting the current job finish, one thread only, and restart.

`tests/test_migrations.py` compares each table's DDL clauses as a set (since B3), because Alembic's batch rebuild emits constraints in a varying order. It also checks that B3's downgrade keeps every track.

Added in B5 (Recommendation Policy v1):

- `tests/test_policy.py`, pure and deterministic:
  - **Constants:** the spec values under one version; invalid constants refused.
  - **Legacy preservation:** for every CSV song and three profiles, intent fit equals `score_candidate()`'s normalized score, over the same features.
  - **Stages:**
    - feature fit over common features only, with weighting and scaled tempo;
    - `candidate_similarity()`;
    - session fit (neutral without evidence, and the spec formula with recency, checked numerically);
    - stage-weight renormalization;
    - current intent winning over history, and history filling only what intent leaves open.
  - **Acceptance scenarios:**
    - no feedback;
    - positive feedback;
    - an early skip (−0.5) against Not for me (−1.0);
    - Not for me (excluded, similar tracks lowered);
    - conflicting intent;
    - missing features (never filled in; tracks with no score last);
    - a finite library (shrinking cooldown, rotation, rejected tracks not using up the cooldown, a one-track library);
    - automatic exploration (its rate, which controls do not move; success and failure, window, cap; which track; no plausible track; unscored tracks; a short queue);
    - listener controls as deterministic one-refresh directives, part of current intent:
      - without a control, exploration stays in the requested genre, even when a track outside it would be plausible;
      - Surprise me takes the last slot, preferring novelty within the genre and setting the genre aside only when the genre has none;
      - Try something different makes a track outside the genre the next to play, even when the genre has novelty;
      - More familiar suppresses exploration that would otherwise happen;
      - no qualifying track means no change;
      - the rest of the queue is unchanged;
    - setting the genre aside without inventing a score:
      - in genre-only libraries, the fallback rule applies, and the pick has no score;
      - a scored track comes before one admitted by the rule;
      - a rejected genre stays out, even when it is the only option;
      - unknown and refused tracks are never admitted;
    - unscored picks surfaced without a score;
    - the #2 threshold (within and beyond the margin, inclusive at zero, nothing played, a less novel #2, a same-artist #2, an exploration pick at #2 or at #1, an unscored #2 behind a scored #1).
  - **Diversity:** repeated artist (including the artist that just played); unknown artists never repeats; near-duplicates; a genre-only library not treated as duplicates; diversity never overriding intent.
  - **Library tracks:** projection to candidates with only the values a track has, and availability.

Added in B6 (feedback and playback events):

- `tests/test_feedback_policy.py`, pure:
  - **Constants:** the register's weights, and validation of the bands and weights.
  - **Passive boundaries:**
    - nothing, 8.0 s, and 8.01 s;
    - 14.99/15, 39.99/40, 74.99/75, and 89.99/90%;
    - 100%, and over 100% (capped);
    - 15% of a longer track; short tracks within and past the grace period;
    - SKIP and COMPLETE read alike.
  - **Explicit actions:** they keep their weight whatever was played.
  - **Precedence:**
    - the latest playback decides without an explicit action;
    - the grace period is no evidence;
    - an explicit action wins in either order;
    - Not for me outweighs a full play;
    - the latest explicit action decides the evidence (changing one's mind), while any Not for me, turn or event, keeps the exclusion;
    - turns and events are read together;
    - a NEXT turn alone is no evidence.
  - **From history to evidence:**
    - one piece per track, newest first;
    - a double Like counts once;
    - a Like on a queued card still decides after a refresh re-surfaced the track;
    - a track heard twice is one piece;
    - a Not for me event excludes; a later Replay turns the evidence positive but keeps the track excluded (D18);
    - exploration outcomes follow the deciding occurrence;
    - stray events are ignored;
    - the same raw facts are read differently under other thresholds.
- `tests/test_feedback_service.py`, against a migrated database:
  - **Reactions:** Like and Save re-rank at once and do not touch playback.
  - **Not for me:**
    - on the playing track, it moves on and keeps the track out for the session;
    - a new session plays it again;
    - on a queued track, it leaves playback alone.
  - **Playback endings:**
    - an early skip moves to the prepared next track and lowers similar tracks;
    - a grace-period skip moves on with no evidence;
    - a completion counts +0.80;
    - a Like takes precedence over the skip that follows, including when a refresh re-surfaced the track in between;
    - a late report after NEXT moves nothing.
  - **Replay:**
    - of a past track: a fresh listener-replay occurrence, ignoring the cooldown;
    - of the playing track: no change;
    - a replay is not a refresh, so a pending control still applies;
    - a Replay after Not for me plays the track manually, but the track never comes back automatically (D18).
  - **Raw events:** each is stored with its own occurrence, even when the evidence is combined per track.
  - **Refusals, leaving nothing stored:**
    - skipping or replaying a track that never played;
    - a playback type sent as a reaction and the reverse;
    - negative seconds, a zero duration, missing seconds;
    - an unknown type;
    - an ended or unknown session, or another session's occurrence.
  - **Exploration and storage:**
    - an early skip of an exploration pick halves the automatic rate;
    - the stored rows hold raw facts only, in order.
- `tests/test_session_service.py`: More like this leaves playback alone; a Not for me turn about the playing track moves on.

## Test Layers

### Unit Tests

Cover pure logic:

- Preference and context validation
- Similarity functions
- Candidate scoring and missing-feature renormalization
- Ranking and tie-breaking
- Diversity re-ranking and cooldown
- Exploration and queue selection
- Feedback interpretation
- Profile update rules

### Integration Tests

Cover module cooperation:

- CSV adapter with recommendation service
- Repositories against a test SQLite database
- Library import against temporary source and media folders
- Background worker and job recovery
- AI adapter with mocked provider response *(Future)*
- YouTube adapter with mocked HTTP response *(Future)*

### API Tests

Cover:

- Request validation
- Response schema
- Status codes
- Error format
- Dependency failure handling
- Request limits

### End-to-End Tests

Cover one complete local journey: import, start a session, play, give feedback, see the queue adapt, restart, and find the library and history intact (spec §30).

### Manual User Testing

Ask test users to complete tasks and report:

- Whether input controls are understandable
- Whether results feel relevant
- Whether explanations make sense
- Whether errors are understandable
- Whether the product is responsive enough

## External Service Rule

Ordinary pytest runs make no real provider network calls (spec §27). Prototype 1 has no providers; when Future AI or YouTube work begins, it uses fixtures and mocked clients.

## Test Data

Keep stable fixtures for:

- Internal songs (`backend/data/songs.csv`)
- User profiles and listening contexts
- Missing metadata
- Small generated audio files for import and analysis tests (B2, B3)
- YouTube search responses *(Future)*
- AI structured outputs *(Future)*
- Provider errors *(Future)*

Tests never read from or write to the real `backend/data/intentune.db` or `backend/data/media/`.

## Continuous Integration

**Future.** No CI workflow exists (`.github/` is absent). A later GitHub Actions workflow should:

1. Check out code.
2. Install the supported Python version.
3. Install dependencies.
4. Run formatting or lint checks.
5. Run pytest from `backend/`.
6. Run the frontend tests, build, and lint.
7. Fail the workflow when required checks fail.

## Definition of Done for a Feature

A feature is complete only when:

- Behavior is documented
- Tests cover the main path
- Tests cover important failure paths
- Existing tests still pass, without weakened assertions or raised timeouts
- Manual behavior is verified when applicable
- Relevant documentation is updated
