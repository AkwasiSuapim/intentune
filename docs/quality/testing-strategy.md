# Testing Strategy

## Status

**Current and Planned.** Reconciled with Prototype 1 in Phase B0 (2026-10-18).

## Goals

- Protect existing behavior during refactoring
- Verify business rules independently of frameworks
- Avoid live external calls during normal tests
- Test errors and edge cases, not only successful paths
- Make results repeatable and deterministic
- Never claim an algorithm improvement without comparison evidence

## How to Run

### Backend

From `backend/`, with the backend virtual environment active:

```text
python -m pytest -q
```

The suite must run from `backend/`, because tests import `src.…` and there is no pytest configuration file. `tests/conftest.py` (B1) provides database fixtures only. At B0, running from the repository root failed collection with 8 import errors. Outside the venv, the system Python on the B0 machine has no pytest.

Persistence tests create their own SQLite files under pytest's `tmp_path` and upgrade them with the real migrations. They never open `backend/data/intentune.db` or depend on `DATABASE_URL`.

API tests (B8) run the real app, startup included, through Starlette's test client (`tests/conftest.py`: `api_settings`, `client`, `library_tracks`). It runs over a fresh database file and media folder under `tmp_path`. The analysis worker and the startup scan are off, except in the tests about them. A generator that never explores automatically keeps queues predictable. The test client prints one deprecation warning (its httpx support); it is expected.

Run the full suite after every phase (spec §28).

### Frontend

From `frontend/`:

```text
npm test                # Vitest: unit, static-render and DOM tests
npm run build           # typecheck and production build
npm run lint            # oxlint
npm run check:browser   # headless-Chrome browser checks (not part of npm test)
```

What B10's tests cover:
- **The gate:** 1, 2, or 3 strong signals change nothing; 4 in one session change nothing; 4 consistent across 2 sessions make exactly one adjustment; different values are never pooled; contrary evidence offsets; rejections alone set nothing.
- **Distinct tracks (review):** four strong items about one track across sessions set nothing, for genre and for a numeric feature; a second distinct track lets the gate pass; duplicates within a session stay collapsed.
- **More like this (review):** repeated More like this turns stay strong session evidence but never reach the long-term gate; a Like followed by More like this is one long-term item, from the Like.
- **Feedback semantics, through the real use cases:**
  - Like counts, and Unlike cancels it without counting against;
  - Not for me is strong negative, as an event and as a turn;
  - skips and partial plays never count, while 90–100% completions do;
  - a Like, a Save, three playlist adds, and a run of Replays about one track in one session are one item.
- **Missing data:** genre-only tracks change genre and nothing numeric; a feature a track lacks is never inferred.
- **Numeric features, on synthetic candidates:** establishment at the batch median; incoherent or concentrated values change nothing; one bounded step per later batch; rejections move away but cannot set; tempo's own span and step; a change of direction breaks a run.
- **The audit trail:** policy version, before and after, cause, reason, and the exact LIKE event ids. The database refuses an unknown event or adjustment, an item with no raw fact, a zero weight, a duplicate item, a taken sequence, and a genre change without its value.
- **Persistence:** the migration round trip keeps the raw history and rebuilds the same profile; a restart keeps the profile and its trail.
- **Recomputation:** identical history in any order gives an identical profile; a withdrawal is recorded as `GATE_LOST`; displacement from the bounded list is `DISPLACED`; an off-path value is `RECOMPUTED`; adapting again records nothing.
- **Ranking:**
  - without history, the outputs are as before;
  - a new session ranks with the separate long-term stage;
  - explicit intent outranks a conflicting preference;
  - history never fills the intent stage;
  - missing long-term features are omitted and the stage renormalized;
  - long-term preference as positive affinity (review): a mismatch is neutral and a full match 1.0; with no intent, strong session evidence for genre B beats a stored preference for A, at the policy and through the real use cases; with the session silent, the preference still lifts A; explicit intent beats both; negative session evidence overcomes a conflicting preference; no profile leaves the pre-B10 scores.
- **Carry-forward:** a library mood makes mood usable; Tune offers only curated moods present; a typed library mood is accepted.

24 single-rule mutations each make a test fail (5 of them for the review corrections). The first draft of two hierarchy tests passed trivially: a tie decided by the tie-break, and a Not for me that had also removed the preference. They were rewritten to state what the formulas do.

Added in B5 (Recommendation Policy v1):

- `tests/test_policy.py`, pure and deterministic:
  - **Constants:** the spec values under one version; invalid constants refused.
  - **Legacy preservation:** for every CSV song and three profiles, intent fit equals `score_candidate()`'s normalized score, over the same features.
  - **Stages:**
    - feature fit over common features only, with weighting and scaled tempo;
    - `candidate_similarity()`;
    - session fit (neutral without evidence, and the spec formula with recency, checked numerically);
    - stage-weight renormalization;
    - current intent winning over history, and history filling only what intent leaves open.
  - **Acceptance scenarios:**
    - no feedback;
    - positive feedback;
    - an early skip (−0.5) against Not for me (−1.0);
    - Not for me (excluded, similar tracks lowered);
    - conflicting intent;
    - missing features (never filled in; tracks with no score last);
    - a finite library (shrinking cooldown, rotation, rejected tracks not using up the cooldown, a one-track library);
    - automatic exploration (its rate, which controls do not move; success and failure, window, cap; which track; no plausible track; unscored tracks; a short queue);
    - listener controls as deterministic one-refresh directives, part of current intent:
      - without a control, exploration stays in the requested genre, even when a track outside it would be plausible;
      - Surprise me takes the last slot, preferring novelty within the genre and setting the genre aside only when the genre has none;
      - Try something different makes a track outside the genre the next to play, even when the genre has novelty;
      - More familiar suppresses exploration that would otherwise happen;
      - no qualifying track means no change;
      - the rest of the queue is unchanged;
    - setting the genre aside without inventing a score:
      - in genre-only libraries, the fallback rule applies, and the pick has no score;
      - a scored track comes before one admitted by the rule;
      - a rejected genre stays out, even when it is the only option;
      - unknown and refused tracks are never admitted;
    - unscored picks surfaced without a score;
    - the #2 threshold (within and beyond the margin, inclusive at zero, nothing played, a less novel #2, a same-artist #2, an exploration pick at #2 or at #1, an unscored #2 behind a scored #1).
  - **Diversity:** repeated artist (including the artist that just played); unknown artists never repeats; near-duplicates; a genre-only library not treated as duplicates; diversity never overriding intent.
  - **Library tracks:** projection to candidates with only the values a track has, and availability.

## Continuous Integration

**Current (2026-10-21).** `.github/workflows/ci.yml` runs on every push and pull request, with read-only repository access. It has two jobs, both on `ubuntu-latest`. A failing step fails the workflow.

| Job | Setup | Steps (each must pass) |
|---|---|---|
| Backend | Python 3.11 (`actions/setup-python`, pip cache keyed on `backend/requirements.txt`) | `python -m pip install -r requirements.txt`, then `python -m pytest -q`, from `backend/` |
| Frontend | Node 24 (`actions/setup-node`, npm cache keyed on `frontend/package-lock.json`) | `npm ci`, `npm test`, `npm run lint`, `npm run build`, from `frontend/` |

- **Versions:** Python 3.11 is the backend's development version. Node 24 is the current LTS within the frontend dependencies' supported range (`^22.22.2`, `^24.15.0`, or `>=26`, from jsdom's engines).
- **Not run in CI:** the frontend's headless-Chrome browser checks (`npm run check:browser`), which need a local Chrome. There is no deployment, merging, or other automation.
- **The symbolic-link test** (`test_local_folders.py`) is not special-cased. It skips only where creating a symlink fails, as on the Windows development machine, and runs normally on Linux, which allows symlinks.
- **Checked before adding the workflow,** since no Linux machine was available locally:
  - every pinned backend requirement, transitive ones included, has a Linux wheel for Python 3.11; soundfile's bundles its own libsndfile, and the one test that names the decoder version reads it at run time;
  - the lockfile lists the Linux builds of the frontend's native packages (oxlint, rolldown, lightningcss);
  - all 238 relative frontend imports match their files' exact casing (Linux is case-sensitive);
  - `npm ci`, `npm test`, `npm run lint`, and `npm run build` pass on a fresh copy of the tracked frontend files.
- **The workflow's first run on GitHub is the Linux verification.**

## Definition of Done for a Feature

A feature is complete only when:

- Behavior is documented
- Tests cover the main path
- Tests cover important failure paths
- Existing tests still pass, without weakened assertions or raised timeouts
- Manual behavior is verified when applicable
- Relevant documentation is updated
